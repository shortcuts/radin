# Decisions and constraints

This file holds what the code cannot say: a constraint, a decision, and the reason.
Structure, verbs, formats and layout live in the code:

- **Flow:** [lifecycle diagrams](lifecycle.md).
- **Who calls what:** the codebase-memory-mcp graph (`search_graph`, `trace_path`, `get_architecture`).
- **CLI verbs and exit codes:** the usage comments in `lib/radin-backlog.sh`, `lib/radin-state.sh` and `lib/radin-scope.sh`, and `radin help`.
- **Shipped files:** `SHIPPED`.
- **Plan template:** `skills/radin-plan/SKILL.md`. **Plan shape check:** `PLAN_SECTIONS` in `lib/radin-backlog.sh`.

A new rule goes here as one bullet: the rule, then `**Why:**`.

## Platform and install

- **macOS and Linux only.** No Windows.
- **Never branch on `uname`.** Resolve tools with `command -v` or `brew shellenv`. Branch only where a tool differs (`md5` versus `md5sum`).
- **Stay bash 3.2.** macOS freezes `/bin/bash` at 3.2. No `declare -A`, no `mapfile`, no `${var,,}`. A newer bash on `PATH` hides a violation, so test against `/bin/bash` or grep. `tests/bash-compat.bats` pins it.
- **The stack is opinionated, and each companion install is advisory.** Installing radin installs every companion, with no per-tool question. **Why:** a skill that delegates to a missing tool cannot work. A failed companion install warns and the run continues.
- **Host text lives in whole-line blocks.** `<!-- host:NAME[,NAME] -->` opens and `<!-- /host -->` closes, each alone on its line, with no nesting. NAME is a file `lib/forbid-NAME.txt`. `scripts/render-host.sh` keeps a block only for a listed host and fails when a string of `lib/forbid-HOST.txt` survives. `scripts/check-prose.sh` fails on a new forbidden string outside a block. `hosts/forbid-baseline.txt` lists the existing pairs, only shrinks, and fails when a pair goes stale. **Why:** whole-line markers keep the source plain text and leave no blank-line residue. The baseline lets existing Claude-only text stay until its entry wraps it.
- **The installer asks every question in one wizard before the first write.** On a terminal the steps are Hosts (a checkbox list), Models and Package manager. Left arrow, Backspace or `b` goes back one step. The last answer starts the install and prints the Review box as a summary, with no confirmation. The models question changes what a run does. The package manager question exists because installing `rtk` through a manager the user does not run adds one they never chose. `--yes` skips both. The installer never asks for the sub-agent effort: each model keeps its default. A new question must be recorded in `manifest.json`, or `radin update` resets it. `radin update` asks none: it reads the models and the package manager from the manifest and prints the Review box as a Recap. **Why:** a question asked mid-install cannot be revisited, and a cancel there leaves a partial install. Asking first keeps every write after the last answer.
- **The numbered fallback has no back.** A piped answer, `--yes` and a missing terminal use `prompt_pick`'s numbered list, one answer per line in the order Models, Package manager. Hosts is terminal-only and a piped run never asks it. **Why:** scripts and CI feed that order, and a back key has no meaning without a keyboard.
- **Never vendor or fork a companion.** `install.sh` reaches each tool through an existing install path.
- **`~/.claude` is not ours.** Rules and exceptions are in `AGENTS.md`.
- **Tests never touch the real device setup.** `make test` unsets `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME` and `OPENCODE_CONFIG`, and fails when the checksum of a real `settings.json`, `~/.claude.json`, Codex `AGENTS.md`, `hooks.json` or `config.toml`, opencode `AGENTS.md` or `opencode.json`, or `~/.radin/manifest.json` changes. Each bats file calls `isolate_env` from `tests/helpers/isolate.bash`. **Why:** a test run under `cc a|b` once overwrote `~/.config/.claude/settings.json`. `CLAUDE_CONFIG_DIR` pointed at symlinks back to that file, and a stub's `cp` followed them. The user lost hooks, statusLine, permissions and plugins, and later installs snapshotted the bad file. Commit 830625a fixed one test file only. An uninstall run that inherits a real `CODEX_HOME` would strip a real radin block.
- **Install hides ponytail's band.** `install.sh` writes `off` to `~/.claude/.ponytail-band` when the file is absent. **Why:** the band is noise for most radin users, and `/ponytail band on` removes the flag. A reinstall hides it again.
- **`unslop` and `technical-writing` are fetched unpinned from cursor/plugins `main`.** **Why:** upstream edits should reach the agents. The cost is that they change agent behavior without review. Three guards: the download must start with `---` frontmatter, a skill directory that `manifest.json` does not record as radin's is skipped, and a failure only warns.
- **The agents host fetches its companion skills from `lib/companion-skills.txt`, unpinned.** Each row names a skill, its companion, the upstream directory and the files `SKILL.md` links. `install.sh` fetches a row into `~/.agents/skills` when no checked dir has it (`~/.agents/skills`, plus the opencode skills dir for opencode), or when `manifest.json` lists it in `agents_skills`. All files of a row land together or not at all, `SKILL.md` must start with `---`, and a failure only warns. **Why:** Codex and opencode have no Claude plugin, and caveman's opencode installer omits `surgical-patch`, `safe-refactor` and `lean-build`.
- **radin's home is `~/.radin`, with rendered `.md` only under `hosts/<host>/lib`.** `~/.radin/lib` holds host-neutral `.sh`, `.c` and `.txt`. `SHIPPED` marks the two kinds `lib` and `hostlib`, and `scripts/shipped.sh check` enforces the split. **Why:** a second host needs its own render of each `.md` beside one shared set of scripts, and `~/.claude` belongs to Claude Code. Repo-side state lives in `<repo>/.radin`, shared by every host.
- **`install.sh` picks hosts from a `HOSTS` table, in a fixed order.** `--only ID[,ID]` wins. Otherwise `--update` reuses the manifest `hosts`, a terminal gets a checkbox list of the detected hosts with claude preselected, and anything else installs claude only. `--list` prints `id`, label and detected, and `--dry-run` prints every write and command, and neither changes anything. `--force` backs up a conflicting path instead of skipping its host. An unknown flag or id exits 2 before any write. There is no `radin install` subcommand. **Why:** a script run without a terminal must keep installing what it installed before, and a typo in `--only` must not fall back to claude silently. A host whose CLI is missing still gets radin's own files, with a warning.
- **The installer checks every host-specific target before the first write, and moves nothing without `--force`.** A path is `free`, `current`, `edited` (listed in the manifest `files` map, digest differs) or `unowned` (there, not listed). A skill directory with no owned `SKILL.md` is unowned as a whole. A manifest without `files` owns every skill and hostlib file it names. An unowned path drops every host that reads its render. An edited file is kept and reported, and the manifest keeps its old digest, so the next run reports it again. `--force` moves either to `~/.radin/backups/<timestamp>/<path under $HOME>` and records the move in the manifest `backups` map. A render that fails its forbid check drops its hosts only. **Why:** the user owns `~/.claude` and `~/.agents`. A backup beside a skill would load as a second skill of the same name. `~/.radin/lib` and `bin` stay overwritten: they are radin's own.
- **`--dry-run` prints the paths the manifest records.** Both read `owned_paths`, which reads the source tree. **Why:** a second list would drift from the first. The report prints companion commands from the same variables the run executes, and runs none of them.
- **Manifest v2 adds `manifest_version`, `hosts`, `agents_clis` and `files`.** `files` maps each radin-owned path under `$HOME` to its sha256, taken after the last edit of the file. `backups` maps each path `--force` moved to its original. A kept file keeps its old digest. A manifest without these keys reads as a claude-only install. `radin-uninstall.sh` reads `hosts`, `agents_clis`, `opencode_allow` and `files` from it and acts on a path only when its digest matches or `--force` is set. `radin-doctor.sh` reads only the keys named below. **Why:** the digests let uninstall remove only bytes radin still owns, and `agents_clis` tells it when the agents render has no CLI left.
- **`SHIPPED` is the one list of shipped files.** `make gen` writes it into marked blocks of `install.sh`, `radin-doctor.sh` and `radin-uninstall.sh`. **Why:** the installed scripts read no list at run time, so `curl | bash` works and uninstall still acts on a broken install.
- **`radin-doctor.sh` judges a shipped file from `SHIPPED` and the filesystem, never from the manifest, except the host list, `agents_clis`, `opencode_allow` and the `files` digests.** `radin-uninstall.sh` falls back to `SHIPPED` when the manifest has no `files` key. **Why:** a stale manifest must never produce a false OK, and a host list cannot come from the filesystem, because `~/.agents/skills` exists on machines that never chose that host.
- **`radin uninstall` takes `--dry-run` and `--force`. A digest of `-` means radin never owned the file, so not even `--force` deletes it. Directories go only with `rmdir`.** **Why:** a skill runs the CLI without a terminal, so it asks first from the dry-run output and re-runs with `--force`. A foreign file in a radin directory keeps the directory.
- **Doctor reports Codex hook trust and the Codex skills listing as notes, and treats a digest mismatch as a failure.** **Why:** Codex stores trust as a hash it computes itself, so doctor cannot re-verify one, and the `codex debug prompt-input` probe has never run against a live Codex. A digest mismatch means a file differs from what install wrote, which is what `files` exists to find.
- **Four things no shipped file may state literally.** `install.sh` writes each one in and exits non-zero if its token survives.
  - `RADIN_CLI`: bare `radin` when the symlink is on `PATH`, else `"$HOME/.radin/bin/radin"`.
  - `RADIN_MODEL_<ROLE>`: the install-time pick. Major roles (planning, execution, review, debug) default to sonnet. Minor roles (fact-finding, and the execution of a task marked `complexity low`) default to haiku. A new role needs a token and a `-e` clause in `set_role_models`.
  - `RADIN_EFFORT_<ROLE>`: always empty, so `radin prompt` prints no `effort` line. A new role needs a token and a `-e` clause in `set_role_efforts`. **Why:** a default changes only after a before/after on tokens per task with `clean%`, failed rate and debug rate not worse.
  - `RADIN_LIB`: `$HOME/.radin/hosts/claude/lib`. **Why:** the Read tool takes no `$HOME`.
- **`radin update` is the one update path and needs no model.** A dev clone runs `git pull --ff-only` and refuses on a dirty tree. Any other install downloads the newest `install.sh` from `main`. `--update` skips reinstalling a companion that is present but still configures it. `--update` refreshes every host in the manifest and asks nothing. A host whose render fails or meets a path radin does not own stays untouched and stays in the manifest. **Why:** the next update retries it; a host dropped from the manifest turns its own files into unowned ones.
- **Edit `skills/*/SKILL.md` in this repo, never the installed copy.** `thermo-nuclear`, `unslop` and `technical-writing` are not in this repo.
- **Install the whole companion, then bracket its destructive write.** `codebase-memory-mcp` installs with `--skip-config`. `radin-cbm-config.sh install` then runs upstream's configuration between a snapshot and a restore. **Why:** upstream [#1200](https://github.com/DeusData/codebase-memory-mcp/issues/1200) replaces the whole `SessionStart` array in `settings.json` and drops other tools' hooks. Leave the bracket in place after the fix. It then prints `INTACT` and covers the next regression. Apply the same test to any future companion.
- **A source edit that changes the Claude render runs `make golden` and commits the new list.** `tests/golden-claude-render.sha256` holds a sum for each installed `SKILL.md` and `lib/*.md`. **Why:** the list is the proof that Claude users see the same text after a change.
- **Codex companions run after the companion installers, not in the per-CLI hook.** `install.sh` runs caveman, ponytail, `rtk init -g --codex` and `codebase-memory-mcp install -y --clients=codex` once rtk and codebase-memory-mcp exist. **Why:** `install_host_companions` runs during the render, before those two binaries are installed.
- **`hooks.json` is copied to `~/.radin/backups`, never restored.** radin edits no `config.toml`, `hooks.json` or role file in `$CODEX_HOME`. **Why:** `radin-cbm-json restore` handles Claude's two files, and the Codex `hooks.json` shape is unverified.
- **The Codex codebase-memory-mcp step is unverified against [#1200](https://github.com/DeusData/codebase-memory-mcp/issues/1200).** The installer may replace the `SessionStart` array in `hooks.json`. **Why:** no Codex binary was available to run it, so the backup copy is the only guard.
- **Trusting new Codex hooks is the user's step.** The installer prints it and `radin` cannot do it. **Why:** Codex asks the user to review new hooks once in `/hooks`.
- **opencode agent files come from `hosts/opencode-agent.md`, written for opencode.** The installer renders one `radin-<kind>.md` per dispatch kind into `$XDG_CONFIG_HOME/opencode/agents`, with no `model` line and `question` and `task` denied. Claude's `tools: [...]` array never appears. **Why:** that array stops opencode 1.x booting ([caveman #386](https://github.com/JuliusBrussee/caveman/issues/386)), and a leaf that cannot ask or spawn cannot hang the router.
- **The opencode allow rule goes in last, with a backup, and is printed when the file is unsafe.** `radin-cbm-json ensure-ext-dir` sets `permission.external_directory."<RADIN_HOME>/**"` to `allow`, once the companions have written the config. `OPENCODE_CONFIG` picks only the file that gets the rule. The helper refuses JSONC (exit 1) and a string `external_directory` (exit 3), and the installer prints the exact rule instead. **Why:** `plugin add` and codebase-memory-mcp both write that config, so the last write is the restore, and a hand-edited config is the user's.
- **opencode companions run after the companion installers, like Codex.** caveman, ponytail, `rtk init -g --opencode` and `codebase-memory-mcp install -y --clients=opencode` run once rtk and codebase-memory-mcp exist. **Why:** `install_host_companions` runs during the render, before those two binaries are installed.

- **A selected host whose CLI is missing fails open.** radin still writes its own files for that host. The companion steps that need the CLI warn and skip. **Why:** the user chose the host, and a missing CLI is a setup gap, not a reason to stop the install.
- **Codex and opencode share `~/.agents/skills`.** One agents render serves both, and `radin doctor` prints one note when both CLIs are present. A conflicting skill of the same name elsewhere is user configuration. **Why:** both CLIs read that root, so a second copy per host would load twice.
- **The agents render passes `--host agents` on every `RADIN_CLI` call, and `bin/radin` with no host picks `agents` under `OPENCODE=1`.** An explicit `--host` or `RADIN_HOST` wins. **Why:** the host now selects only companion skill names and the render directory, and `radin_skill` runs at call time in scripts. Codex sets no marker that radin checks, so the render flag carries it.
- **`radin update`, `radin uninstall` and `radin doctor` act on every installed host, with no per-host flag.** The manifest records the hosts and the agents CLIs. Uninstall removes the agents render only when no agents CLI remains. **Why:** one run per action keeps a multi-host install from repeating the same setup for each host.
- **Verification has three layers, and none is optional before the host support counts as stable.** The layers are offline `make test`, an opt-in `make verify-hosts` that drives the real opencode and codex CLIs in an isolated HOME without a model call, and a manual end-to-end checklist on both hosts. **Why:** the offline tests cannot show that a real CLI loads radin's files.
- **`make verify-hosts` drives the real CLIs with `--standalone`, a stubbed `PATH` and one `HOME` per host.** **Why:** `opencode debug` without `--standalone` reaches the user's background service and real config, and a failing companion download only warns, so the stubs keep the run offline.
- **A plain install leaves a present companion alone, and `--refresh` upgrades it.** `.radin/bin/.radin-*.sum` and `.radin/cbm-wired.stamp` skip an unchanged C build and an unchanged codebase-memory-mcp wiring. Progress lines print only with `--details` or `RADIN_DETAILS=1`; each step otherwise prints one line with its time. **Why:** reinstalling every companion took ~180s of a ~6s install, and 30 progress lines hid the one warning that needed the user.

### Limits of the codebase-memory-mcp bracket

Read these before you change `lib/radin-cbm-config.sh` or tell a user they are covered.

- **Two files, one client.** The snapshot covers `~/.claude/settings.json` and `~/.claude.json`. Every other client upstream configures takes its write unbracketed. Never claim radin protects a config it did not copy.
- **Install moves `~/.claude/.radin` to `~/.radin` once, through `~/.radin.migrating`.** It acts only when the old directory holds a radin manifest (`installed_at` and `companion_tools`). A `~/.radin` without one, or a leftover `~/.radin.migrating`, aborts before any write. A `~/.radin` with one skips the move and leaves the old directory. A failed `mv` leaves the old directory intact and stops. After the move, install deletes the pre-split `.md` and retired files from `~/.radin/lib`, and `unallow-legacy` removes the old `Read` pair. **Why:** a cross-device `mv` copies, then deletes, so a copy that dies halfway must never leave a `~/.radin` that passes the manifest test. The staging name makes the last step a same-directory rename.
- **Install adds two `Read` rules for `~/.radin/**` to `permissions.allow`.** One rule covers the `~/.radin` spelling and one the resolved path when it is a symlink. `radin-cbm-config.sh allow` adds them, `unallow` removes those strings and the two legacy `~/.claude/.radin/**` ones, and `radin-cbm-json` writes through a symlinked `settings.json`. **Why:** skills and leaves read `lib/*.md` from outside the repo, and Claude Code asked before each read in every repo. A Read rule is per user and covers radin's own files only. Bash stays unlisted, because a shell grant would cover far more than radin ships.
- **Restore, not rollback.** It adds back entries the snapshot had and the file now lacks. It never deletes an upstream entry. `codebase-memory-mcp uninstall` does that.
- **Upstream's own entries are never restored.** An entry naming `codebase-memory-mcp` or a `cbm-*` shim is upstream's. Upstream rewrites those spellings between versions, and restoring the old one pins a dead path in `SessionStart`.
- **A hook command naming a missing path is pruned, whoever wrote it.** A `~/.claude` shared between machines carries the other machine's `$HOME`. A bare shim name is never pruned, because it resolves against Claude Code's `PATH`.
- **Doctor fails on a hook command that is not on `PATH` and not an executable path.** It judges bare names against its own `PATH`; `sh -c` strings are not parsed. **Why:** a leaked test fixture left a bare `caveman-session` that failed every session start while doctor said OK. Prune stays path-only because it deletes.
- **Upstream's `cbm-*` hook scripts are moved, never deleted.** They bake in an absolute `BIN=` path. `install` moves them to `~/.radin/backups/hooks.<stamp>/` so upstream writes them again for this machine.
- **A stale `mcpServers` command is replaced.** `adopt_staged_mcp` overwrites an entry whose `command` path does not exist.
- **A hook `command` must be an absolute, unquoted path.** Measured on Claude Code 2.1.236 and 2.1.24x. A single-word command is `posix_spawn`ed verbatim, so `~/...` and a quoted path die with `ENOENT`. Only a command with further words reaches a shell. `normalize_cbm` rewrites `cbm-*` hook commands and leaves other tools' alone.
- **Newest snapshot wins.** `repair` reads the newest `*.bak` pair. That is right after an upstream `update` and wrong for rebuilding a much older config.
- **The compiled JSON helper gates the path.** `lib/radin-cbm-json.c` does every JSON read and write. With no compiler, `install.sh` skips upstream's configuration and falls back to merge-only wiring. **Why:** a destructive write with no restore is worse than a smaller install.
- **Snapshots are the user's data.** They can hold `env` values. radin never deletes one, and `radin-uninstall.sh` names the directory.
- **Uninstall is asymmetric.** `/radin-uninstall` removes radin's files. Upstream's skill, agents and hooks are upstream's to remove.
- **`radin hooks mcp` writes a machine-specific binary path.** Say so when a user asks about committing `.mcp.json`.
- **A symlinked `~/.claude` is handled, not covered.** Upstream refuses to write under one and exits 0 ([#1722](https://github.com/DeusData/codebase-memory-mcp/issues/1722)). radin resolves the link, passes it as `CLAUDE_CONFIG_DIR`, and adopts the staged MCP entry. A user's own `CLAUDE_CONFIG_DIR` is left alone.
- **Upstream's PATH step exits 1 under fish or bash.** `run_upstream` passes `SHELL=/bin/sh` so the run does not end `PARTIAL`.
- **An upstream exit 0 does not prove configuration.** `cbm_wired` checks for a `cbm-*` hook and the MCP entry by name. An upstream rename reads as absent until the check is updated.
- **Install raises each cbm hook timeout to 10 s and sets `CBM_HOOK_DEADLINE_MS` to 8000.** It never lowers a timeout the user set higher. **Why:** upstream writes 5 s, and on a 248 MB graph Claude Code cancelled about 1 in 5 session-start hooks.
- **One file says which tool answers which question.** `lib/radin-explore-rule.md` holds it, and `radin-prompt.sh` injects it at `EXPLORE_RULE`. **Why:** five paraphrases drifted apart, and only some said to confirm an empty graph result with Grep.
- **The CLAUDE.md section check is not locked.** `ensure_claude_md` checks for the marker, then appends. Two runs at once can both append the section. **Why:** no lock, because no duplicate has a traced cause and a lock adds state to fix a guess; a duplicate section costs only prompt tokens. The `~/.claude/CLAUDE.md` copies a prompt audit found have no known cause and are left alone.
- **MCP tool names exist in one file.** `lib/radin-cbm-hooks.sh` names them, and each must exist in upstream's MCP Tools table. `semantic_query` is a `search_graph` parameter, not a tool. Every skill and prompt names the server, never its verbs. **Why:** a wrong name costs a failed call in every sub-agent. No test pins this, so review does.

## Skills and sub-agents

- **A companion skill name is a token, and one table per host spells it.** Prose writes `@@skill:NAME@@`. `scripts/render-host.sh` and `radin_skill NAME` in `lib/radin-host.sh` read `lib/skill-names-HOST.txt`. The claude value is today's text (`/ponytail:ponytail-review`). The agents value is the bare name. **Why:** one table feeds the renderer and the scripts, so a name lives in one place per host. A script on the agents host cannot detect a skill instruction written with no slash (`SKILL_DENY`). The instruction format on those hosts is not settled.
- **Every entry point is a skill.** **Why:** Claude Code removes `AskUserQuestion` from every sub-agent, and a sub-agent's prose reaches only the calling session. As an agent, radin-batch's Phase 2 gate could never ask. As a skill it runs in the user's thread, asks, accepts interruption and resumes from disk.
- **A sub-agent is a leaf.** It has no prose channel to the user, no `AskUserQuestion`, and no `Workflow`. A prompt that sends one into a skill that asks in prose (`/grilling`), launches a workflow (`/deep-research`) or spawns a background agent and waits (`/research`) ends its turn with no `STATUS:` line. The task then hangs `in_progress`.
  - Needing a fact: dispatch radin's own synchronous fact-finder, never a third-party research skill.
  - Needing a decision: the router asks the user, or records the entry `blocked`.
  - `radin backlog field SKILLS` drops user-named skills of those classes. The Phase 5 summary names each one dropped.
- **Background sub-agents keep a smaller built-in tool set.** `Agent` is not cut from it, so a depth-1 background sub-agent still delegates. Do not read its absence from the second filter's list as removal.
- **On the claude host: no prompt tells a model to set `run_in_background`.** Fork mode (v2.1.232+) removes the parameter. A background leaf's result arrives as a notification in a later turn. The router waits, and treats a dispatch that returns nothing as unfinished.
- **On the claude host: a leaf never waits on a background run, and the router runs a cron heartbeat.** The leaf contract bans ending a turn on `Monitor` or `run_in_background`. The router creates one `CronCreate` job per dispatched task (every 20 minutes at most), deletes it when `task-report` records that task, and checks only that task's agent when it fires. The job fires only while the router's turn is idle. **Why:** a sub-agent gets no background notification, so a leaf that ends its turn waiting is never woken, and the router's own turn ends with no wake source. One session lost 7 hours this way. Cron is native and starts no process. `ScheduleWakeup` serves `/loop` only.
- **The agents loop dispatches a leaf, waits for it, and has no heartbeat or nudge.** A leaf that returns with no `STATUS:` line goes in as `--no-status`. **Why:** a blocking dispatch returns only when the leaf ended, so no idle leaf exists and no notification is pending. Stuck-recovery already covers a dead session.
- **The agents leaf contract omits `Workflow`, `Monitor` and the 4-minute rule.** **Why:** `Workflow` and `Monitor` are Claude notification tools, and the 4-minute rule is a Claude prompt-cache limit. The agents loop dispatches blocking, so no wake source is missing.
- **A leaf keeps each tool call under 4 minutes and polls a longer run in 240-second waits.** **Why:** a sub-agent gets a 5-minute prompt cache even on a subscription. In 696 measured leaves, 130 foreground waits hit the 10-minute Bash timeout, and each one wrote the whole leaf context again: 20.6% of all leaf cache writes. A poll reads the cache at about 0.05× the input price, and a re-write costs 1.25×. A 1-hour sub-agent TTL costs more, because every write then bills at 2×.
- **The agents host asks through `lib/radin-ask-rule.md`.** The rule holds the cap of 3 questions and 3 options per call, the recommended option first, and the plain-text fallback. **Why:** Codex Default mode refuses its structured question tool, and one file keeps the sentence in one place.
- **On the agents host, a sub-agent inherits the parent's model and effort.** The templates keep `model:` and `effort:` lines in claude blocks only, and `radin-prompt.sh` prints no `model` or `effort` line on agents. On claude a missing `model` line still fails. **Why:** the agents hosts give the dispatch no model parameter, so a printed model is a value the router cannot pass.
- **radin ships no background agent.** `claude agents` or `/bg` runs `/radin-batch` unchanged in a full background session. The worktree-per-task answer keeps concurrent sessions apart.
- **`radin-plan` is a skill that runs in whichever context calls it.** A planning sub-agent invokes it non-interactively. Where it would ask, it takes the non-destructive path (no split, no overwrite). On real ambiguity it marks the task `blocked`.
- **`/radin-uninstall` and `/radin-stats` carry `disable-model-invocation: true`.** **Why:** a model-invoked description loads into every session and sub-agent. `tests/skill-names.bats` caps every model-invoked description at 40 words.
- **`/radin-teardown` is a flag, `state/teardown`, that `task-next` honors.** **Why:** the stop must reach the loop without killing a leaf mid-commit. `task-next` exits 1 for any new pick, so Phase 4.5, 4.7 and 5 run unchanged. A named re-run of an in-flight task still goes. `state preflight` clears the flag, so it never outlives its run. The skill carries `disable-model-invocation: true`.- **The router holds the backlog at low resolution.** It carries ids, titles, order and exit codes. Every zoom (a task body, a plan, a diff, code exploration) belongs to a leaf, which hands back one `STATUS:` line.
- **Delegation names are pinned.** `tests/skill-names.bats` pins every `/<name>` in `skills/**/SKILL.md` and `lib/*.md` to a shipped or installed skill. A new companion needs its plugin prefix in that test's list.
- **The execution prompt names `/ponytail:ponytail` and never invokes it.** Ponytail's SubagentStart hook injects the ladder, and invoking it loaded the text twice. The hook is therefore load-bearing: `install.sh` enables a companion plugin found disabled, and `radin-doctor` reports `disabled`.
- **Cold paths live in on-demand files.** `lib/radin-batch-*.md` are read only when a trigger fires (stuck tasks, a block, the first run in a repo, a resume, the gate, a requested review). **Why:** `SKILL.md` sits in the user's context for the whole session.
- **The leaf prompt is assembled, then dispatched by path.** The router sends `Read <path> and follow it.`, never the text. **Why:** echoing a 6KB prompt as an `Agent` argument costs output tokens on every dispatch. The prompt carries the task body inline so the leaf spends no read on it.

### One rule, one file

What an audit checks prose against:

- **One statement per audience.** Skill and lib prose is read by a router or a human-thread skill. A verbatim fence in `lib/radin-prompt-<kind>.md` is read only by its sub-agent, so a fence copy is a payload, not a duplicate. A rule every leaf prompt states lives in `lib/radin-leaf-contract.md` (the `LEAF_CONTRACT` token). The comment rule lives in `lib/radin-comment-rule.md` (the `COMMENT_RULE` token). `scripts/check-prose.sh` fails on a new sentence of 8 or more words stated twice, with an allow list for copies kept on purpose.
- **The code owns deterministic behavior.** Prose names the verb and its exit codes, never what the verb computes.
- **Cross-skill rules live in the `<!-- radin:begin -->` block** that `install.sh` writes into `~/.claude/CLAUDE.md`. It costs no file read.
- **Reporting your own actions is not orchestration.** The bar is deriving data from CLI output: filtering, sorting, joining, counting, subtracting. A skill naming the entries it just added needs no verb.
- **The caller declares non-interactivity.** The dispatching prompt says the sub-agent cannot reach the user. The skill states only the branch defaults a reader cannot derive.

## State and data

- **State lives in the consumer repo at `<repo-root>/.radin/`, shared by every host.** Outside a git repo, `$PWD` takes the repo root's place. **Why:** the earlier `~/.claude/.radin/projects/<slug>/` scheme made the agent trust an opaque hashed mapping, and a per-host directory hid one host's backlog from the other.
- **Telemetry lives in `~/.radin/telemetry/<scope>.jsonl`, one object per event, and a failed write never fails its caller.** Scope names a topic, and each record carries its repo path. **Why:** one grep across `~/.radin/telemetry` shows patterns across repos, and a record must not block the run that makes it.
- **All state is JSON Lines, one compact object per line.** This holds for `index.jsonl`, `BACKLOG_STEPS.json`, `completed.json` and `journal.jsonl`. **Why:** bash 3.2 has no JSON parser and the project has no `jq`, so each CLI op stays a grep or sed one-liner. An edit to one entry never risks another.
- **One file per task.** No agent addresses backlog content by line number. A task's path is always read back from its index line's `file` field, never composed or cached.
- **An epic is one directory level and nothing else.** It gets no index line and no category. **Why:** `list` feeds `radin-batch`, and an epic row would be dispatched as a task. No epics inside epics. Task ids stay globally unique across epics.
- **A task `id` never changes.** `retitle` and `set-category` rewrite one field. **Why:** `depends_on`, plan pointers, `prepare` and the `radin/<id>` branch all key off it.
- **A value a parser reads is a key on the index line, not a `**Label:**` line in the body.** This covers `plan`, `skills`, `acceptance`, `facts`, `location`, `planning`, `priority` and `depends_on`. **Why:** a markdown parser fails silently. A label with its colon outside the bold markers once yielded nothing and told no caller, so a leaf ran with no criteria and reported success. Sorting must also not cost one file read per task. Every key is validated on write.
- **A sentence written for a model is a `**Label:**` line in the body** (`Decision`, `Fact`, `Root cause`, `Raised as`, `Scope`, `Finding`, `Severity`, `Evidence`, `Preferred remedy`). Each binds the next sub-agent that reads the task. A `Fact` or `Root cause` labeled `guess`, or unlabeled, is a lead to check. `measured` means the author ran it. `inferred` follows from measured facts the line names.
- **`priority` is a human decision.** It is one of the Fibonacci values `1 2 3 5 8 13 21`, and `21` is most important. **Why:** seven choices are a smaller decision for an agent than an unbounded integer. An absent key means unset, and no verb ever defaults it, so "did a human decide this?" stays answerable. Validation runs on write only, so a legacy `"priority":70` still loads.
- **`list` orders by priority, descending, with unset last.** That is an ordering contract. The TUI uses `--order created` so no mutation moves a row. `list` separates fields with the unit separator, because a tab collapses under `IFS=$TAB read` when `priority` is empty.
- **`order` composes the execution order and stores nothing.** An inferred rank or dependency arrives as a flag it validates, never as `set-priority` or `set-deps`, so the index stays the human's. A dependency moves up, never a dependent down (see `AGENTS.md`). The index `depends_on` wins over an `--infer-deps` value, and that precedence lives only in `order --steps`.
- **`set-deps` and `add --deps` take ids or titles, each resolved like `find`, and reject a miss, a several-match, a self-reference and a cycle.** **Why:** an unresolvable dependency stalls `deps-check` instead of failing it. `remove` prunes the id from every other entry.
- **`RADIN_HOST` selects skill names and the prompt render, never the state directory.** `claude` is the default, `agents` serves Codex and opencode. `radin --host NAME` is global, only before the subcommand, and `update`, `doctor`, `uninstall`, `hooks`, `wire` and `repair` validate it and ignore it. **Why:** one backlog for every host leaves nothing for the host to select, but `radin_skill` and the prompt render still differ per host.
- **`add` stamps `created` and `branch`.** They are provenance, and no verb rewrites them. A line from before the stamps reads as unknown.
- **Acceptance criteria sit on the index line and add nothing when absent.** **Why:** a synthesized criterion would measure the work against radin's own guess. They are also the only bar for `radin state recover` exit 3. An entry with no criteria gets `recover-reject`, never the router's reconstruction of what the task wanted.
- **The CLI owns every deterministic operation; skills supply judgment.** Id assignment, lookup, ordering, prompt-field rendering and the duplicate scan are computed by code. **Why:** the model used to re-derive them from prose every run. `lib/radin-prioritization.md` holds only the two non-computations: ranking the unset group and inferring a dependency.
- **A state verb answers one step a caller takes.** Claiming, stashing, the debug flag and the completion write are functions, not verbs. **Why:** a verb nobody calls is one more thing a model can reach for.
- **Every verb resolves the namespace from the current directory.** No caller passes a path. A worktree that `prepare` made resolves to the checkout that made it. **Why:** a router that carried `$NAMESPACE_DIR` re-sourced the environment on every call, and one run wrote its own script to do it.
- **`backlog field` and `backlog find` read the main checkout's index when a linked worktree's own index is empty.** Write verbs never borrow it. **Why:** a worktree the user made keeps its own plans and state but not the backlog, and `radin-review` died on "no backlog" and then ran with no spec.
- **`task-report` ends in one `next` line and the router routes on that line alone.** It checks the tree first. A dirty tree is committed as a wip commit and the task retries, whatever the `STATUS:` claimed. **Why:** a leaf that stops before its commit has still done work, and a stash hides it. A wip commit reaches the base only inside one squash commit. `a079a17` and `757c4ec` stay on pushed history, since a rewrite needs a force-push. It also records a planning leaf's `PLANNED` sizing (`planning --none`, `complexity`), with no tree check. **Why:** one writer for index fields, and no `set-meta` in a leaf prompt.
- **A stalled task never asks the user.** No `STATUS:` line, an inconclusive report, a failure after the debug pass, and `MAX_ATTEMPTS` all leave the entry on the backlog with a `**Progress:**` note, keep any work as a `wip(<id>)` commit, and move on. **Why:** the user decides at record time. After that, only a product choice (`BLOCKED (DECISION)`) is theirs, and a process fault is not one.
- **`task-next` is the only claim.** It sets `in_progress` and bumps `attempts`. Past `MAX_ATTEMPTS` (3) the entry goes `blocked`. **Why:** a crash loop must not burn tokens forever. `attempts` resets when a plan lands, or when the user says so through `state retry <id>`, which also clears `debugged`. No other path lifts the cap, so nobody rebuilds the plan to dodge it.
- **An entry's absence from `BACKLOG_STEPS.json` means the task is complete.** `deferred` is written only by `steps-init`, and `set-status` refuses it. **Why:** the excluded set must not have to survive in context between Phase 2 and Phase 5.
- **Phase 1 settles every waiting entry before Phase 3.** **Why:** `steps-init` rewrites `BACKLOG_STEPS.json` every run, so a deferred or inconclusive entry left unanswered would restart without its decision.
- **Phase 3.5 refines every selected task before the first dispatch.** `state steps-open` prints each `**Open decision:**` line a task file holds after its last `**Decision:**` line, and the router grills them once. No sub-agent runs. **Why:** a leaf cannot ask, so a decision it meets mid-run blocks the task and stalls the autonomous run. A refine sub-agent per task read every task to find nothing, because `radin-record` and planning already apply the Fact versus Decision test with the user present. `lib/radin-open-decisions.md` is the one owner of that test. A decision nobody recorded still reaches the user through `BLOCKED (DECISION)`.
- **Phase 5 offers the Phase 0 grilling for every entry still `waiting`.** One `AskUserQuestion` asks "settle now?", and `Yes` runs the same section of `lib/radin-batch-clarify.md` that Phase 0 runs. **Why:** a deferred entry otherwise waits until the next run's Phase 0, and the user, present at the summary, never learns they can answer now. One section owns the grilling, so the two phases cannot drift.
- **The one Debug pass is a `debugged` flag on the steps entry, not a router counter.** **Why:** a counter cannot survive a resume or a compaction. The flag has the lifetime of `attempts`, because `steps-init` rewrites the file every run.
- **`task-done` validates the hash first.** It must be a commit reachable from the branch `prepare` recorded or from the base branch, and it must be in the base branch before the task counts as done. **Why:** the hash comes from a sub-agent's free-text `STATUS:` line, so nothing else checks it. The crash-safe order is: append facts, write `completed.json`, then drop the entries. `completed.json` stores the title and provenance because completion deletes the backlog entry.
- **`prepare` is the only place the worktree and branch answers become git commands.** It also records the branch it read from git. **Why:** a model that sees the answers can talk itself past a `no`. A worktree needs a group of 2 or more tasks that the router recorded with `state group-set`, and `no` still blocks it. **Why:** fewer worktrees means less work for the merge agent at the gate. A dirty tree is stashed first, so no leaf commits or reverts work it did not write. It then applies a stash the router claimed for the task. A tree a leaf left dirty is not stashed. `task-report` commits it (see above).
- **A task worktree is `<repo-root>-<id>` on `radin/<id>`, and only a member of a parallel group gets one.** A task alone takes a branch in the main checkout or commits to the base, per the branch answer.
- **The journal is forensics, never control flow.** Every state mutation appends one event. radin never truncates it. **Why:** an agent whose context compacted can rebuild what the session did (`journal-tail`).
- **A task is done when its commit is in the base branch.** `task-done` on a `radin/<id>` commit the base lacks records nothing in `completed.json`. It writes `state/unmerged/<id>`, journals `done-unmerged`, keeps the backlog entry and blocks it with a note naming the branch. `state reconcile` records the task done once the work lands, and `state unlanded` lists what is still outside the base. A dependent of an unmerged task does not wait for the merge: see the stack bullet in "The run loop". **Why:** a worktree or branch only speeds up work; a task done on a side branch is orphaned work. A skipped Phase 4.7 once left `snackbar-styling-differs-between-screens` done in the backlog and absent from main.
- **A task's long evidence goes to `state/facts/<id>.md`, and `task-done` appends the entry's `Fact` lines there.** **Why:** deleting the entry would otherwise lose them. There is no shared notes file. A leaf gets its own task's material and nothing more.
- **A plan has a fixed eleven-section shape, checked by code.** `plan-lint` runs in `add-plan` and refuses a bad plan, so the plan review spends no tokens on shape. `plan-target` is the only place the `plans/<id>.md` path convention lives. `add-plan` records `HEAD` in `plans/<id>.head`, so a stale plan gets a warning block in the execution prompt. `## Changes` entries must keep the `- \`<path>\` — ...` shape, because `backlog files` parses them.
- **radin enforces no live check.** `plan-lint` and the plan template ask for a `## Testing` check box, never a `Live:` box. Each repo defines its live checks and test harness in its `AGENTS.md` or `CONTRIBUTING.md`, and an agent that finds no harness able to observe a behavior extends the harness in the same task. **Why:** a mandated `Live:` box made agents wait for a human step in clidraw, where a pty harness could run the check.
- **`radin scope` resolves a review scope to `type`, `scope`, `command` and `passes` lines.** Its flags (`--in-scope`, `--commits`, `--specs`, `--attribute`, `--bucket`) each took a branch out of the review skill. `--in-scope` screens fresh citations with no backlog entry yet. The `location` key records where an existing entry's finding sits. They are not one thing.
- **`radin state report` prints the whole Phase 5 summary.** The router prints it verbatim. It reads `baseline.json` to scope "this session".
- **`manifest.json` is rewritten wholesale on every install.** Only `install.sh --update` reads it: `package_manager`, `hosts`, `agents_skills`, and the `unslop` and `technical-writing` booleans as the ownership record.

## The run loop

- **The router makes one startup call, `state preflight`, and reads a side file only for a line it prints.** **Why:** six startup verbs each routed on an exit code. One call prints a tagged line per applicable branch, so the router loads recovery, session and prioritization text only when needed.
- **Resume triage is a CLI verb, `state resume`.** **Why:** the retry rule has no judgment, and per-entry `set-status` calls by the router were error-prone.
- **The router does no per-task verification.** A `SUCCESS` goes straight to bookkeeping. **Why:** a per-task refuter cost an extra sub-agent per success. The leaf verifies its own work, and Phase 4.5 gates the session. Do not reintroduce a refuter, and do not have the router re-read the diff.
- **`task-report` fails a `SUCCESS` whose commit leaves the plan's `## Changes` paths.** A directory path matches by prefix. Tests, `.radin/` and generated output whose input the plan lists (`SHIPPED`, a lifecycle `.mmd`, `lib/radin-tui.c`) are exempt. The failure names each extra file and records a `parallel` `out-of-bounds` telemetry event. `task-done` called by hand only journals `out-of-plan`. The leaf's `test <name>: failed before, passes now` line is evidence for the human, not a gate. **Why:** parallel groups are safe only when each task stays inside its declared paths.
- **The leaf picks its checks from what its diff reaches in the code graph.** **Why:** on a large repo the full suite was 16 of 21 minutes in one measured task. Phase 4.5 runs lint and format, never the test suite, once at the tip of each branch the session touched. There is no per-session choice. `radin state gate-map` renders each branch, tip, worktree and oldest session commit into the gate prompt. **Why:** a leaf should not derive layout the CLI holds.
- **A failed check is re-run for three rounds, then `FAILED`.** A stuck task never loops. The leaf's verify loop comes from the MIT-licensed [cursor/plugins pstack](https://github.com/cursor/plugins/tree/main/pstack) principles `prove-it-works`, `sequence-verifiable-units` and `test-behavior-not-implementation`.
- **A check that fails outside the diff is fixed in the same task.** The leaf stashes, re-runs the check on the base, and fixes a red base through `/caveman:surgical-patch`. A fix out of reach becomes a `fix` entry via `backlog add`, and the task still finishes. **Why:** two clidraw tasks ended `INCONCLUSIVE` on a red base test, which hid a real bug and blocked every later task.
- **The session gate reviews the session's commits and files its `act-on` findings, once.** The gate leaf runs `radin-review-core.md` at level `session`, buckets each finding with `radin scope --bucket`, and adds `act-on` ones through `backlog add`. `state gate-filed` appends them to `BACKLOG_STEPS.json` and writes `state/gate-reviewed`. The loop runs them, the gate runs again with no review block, and the run ends. **Why:** the agent fixes its own mistakes with no human step, and one round cannot loop forever. `steps-init` clears the marker, so a new run reviews again. Consider and Noted findings are dropped here, and `/radin-review` triages them. The second round's fix commits get no review.
- **The session report says "reviewed" only when the gate ran.** The router calls `state gate-done` after a `SUCCESS` line or a line with a `filed` list. `report` then names the session gate instead of "Nothing verified these commits yet". **Why:** `state/gate-reviewed` stays absent when the gate files nothing, so it cannot tell a run gate from a skipped one. `steps-init` clears the new marker.
- **The leaf reviews its own staged diff before it commits** (Step 9, `radin scope staged`, two rounds at most). **Why:** the skill holds the repo's rubrics and the context is warm. The cost is that the same agent that wrote the diff reviews it. The Phase 4.5 gate adds the second look. The skill writes no backlog entry for an agent caller, so a `nit` costs nothing.
- **The review core rates each `diff` and `session` scope `high` or `low` on its own, and every reply ends with a `Blind spots:` line.** `high` means the changed lines delete or overwrite data the task did not create, run outside the repo, handle secrets or auth, or change an interface another program calls. A `low` session skips `/thermo-nuclear`, and a `high` one holds every `warning` to the `traced` rung. **Why:** the Claude Code team spends human review on risky changes and automates the rest ([Osmani, 2026-10-26](https://x.com/addyosmani/status/2114604912520921136)). The model rates, so the loop never asks. The blind-spot line forces a reviewer to say what its passes cannot see before `no findings` reads as proof.
- **`radin-review` prints the triage list once, as reply text, and the Step 4 `AskUserQuestion` repeats none of it.** **Why:** the UI shows a sub-agent's result as a short summary. When the dialog also held the full list, the router dropped the printed copy, and the dialog text is cut short too. Only `/radin-review` reaches this gate.
- **A review sub-agent writes its report to `reviews/<UTC stamp>-<scope>.md` and returns one `REPORT:` line.** `/radin-review` Step 3 and `/radin-plan` Step 4 pass the path. **Why:** the harness cuts a sub-agent's final message at about 4.9K characters. Four deep-review sessions (2026-10) lost the tail, and a free-form user question made the report longer than the one-line-per-finding format. `state/facts` already works this way for leaves. A missing file gets one `SendMessage`, then the review counts as inconclusive.
- **`radin-review`'s plan level reviews on two axes, Standards and Spec.** It costs two sub-agents per plan. **Why:** a missing criterion or a contradicted `Decision` is one markdown edit before any code exists. `/thermo-nuclear` runs once at `session`. **Why:** its body was a third of each planning dispatch, and a plan has no code to judge. Plan-review findings stay in the plan file, because a backlog entry about code nobody has written would come back as work.
- **Planning is unconditional and just in time.** A task with no plan gets a planning leaf, because the router cannot size a task without reading the code. Planning is not batched ahead. **Why:** a wave plan describes a tree that earlier commits then change.
- **Whether a task needs a plan is decided at record time.** `radin-record` flags `planning needed` and appends without a confirmation gate. **Why:** a gate stalled the capture the user asked for, and Step 6 reports every verdict for correction.
- **`radin-record` picks the decision channel per item, after the Fact lookups.** The agent judges the prompt's clarity and the task's complexity and picks grilling, `AskUserQuestion`, or no question, with no user flag. A Decision that stays unsettled still becomes `**Open decision:**`. **Why:** a prompt that is vague or a task that is complex needs a grilling, and a count of Decisions alone cannot tell that. Facts the agent can check first remove questions the user never needs to answer.
- **Complexity, not category, picks the execution model.** Category picks the discipline skill. `radin-record` and `radin-review` size an entry that needs no plan, and the planning leaf sizes a flagged one, both by `lib/radin-complexity-rule.md`. The needs-a-plan rule lives in `lib/radin-planning-rule.md`. Only a `low` task runs on the minor model. An entry with no value runs on the major model and gets no sizing dispatch. **Why:** category records what a change does to the codebase, not how hard it is. A `chore` that tuned constants from device runs went to haiku and failed for hours. A size-only dispatch per unflagged entry costs a sonnet call that saves tokens only when it answers `low`.
- **`radin-batch` and `radin-do` share one body, `lib/radin-run.md`.** **Why:** a change to the loop is a one-file edit, and the two cannot drift.
- **Execution concurrency is derived, never asked.** The worktree answer from Phase 0.5 allows parallel work, and the router records each parallel message with `state group-set` before dispatch. **Why:** parallel agents in one checkout corrupt each other's commits, so a second question could only restate or contradict the first. `task-next`'s `overlap` line comes from plan `## Changes` paths, and the router parallelizes only `none`. Planning, debug and fact-finding dispatches write no repo code, so they run in parallel.
- **`state wave-partition` groups a wave by disjoint plan paths.** It packs first fit under a cap (default 4), prints the shared paths of each pair it keeps apart, and the router may only split a group, never merge two. **Why:** a group of independent tasks is the only safe parallel unit, and the evidence must reach telemetry. The `overlap` line of `task-next` stays until the router uses the partition.
- **`state plan-discard` drops a wave task's plan and flags it for a new planning run.** It resets attempts to 0 and records one parallel telemetry event with the task, wave, kept-apart paths and planning tokens. **Why:** a plan written against the pre-wave tree may be stale once the group lands, and the user reads the telemetry to see what the extra planning bought.
- **Phase 0 and Phase 4.7 run one verb, `state reconcile`, and it lands every `radin/*` branch whatever its task's status.** It skips only a task `in_progress` in the steps file. It wip-commits a dirty worktree, squash-merges the branch into one commit with the tip's subject, removes the worktree and deletes the branch with `-D`. A branch whose work is already in the base (`git merge-tree` changes nothing) is only removed. A finished task is recorded done at the squash commit. An unfinished one (no `state/unmerged/<id>`) first gets a `Finish: <title>` entry that names the task, the commit and the steps note, with a `deferred:` question as its `**Open decision:**`. Its dependents move to that entry, and then the task is recorded done. A failed `-D` or `worktree remove` prints a `merge: kept` line and a `merge-kept` journal event. A conflicting squash resets with `git reset --merge`, writes `state/conflict/<id>` and exits 3. Only then does one `radin-merge` leaf take the conflicting branches, and the router runs `reconcile` again after its `SUCCESS`. The leaf resolves a conflict that keeps both sides' intent and reports `BLOCKED (DECISION)` when two behaviors exclude each other. **Why:** work left on a branch is orphaned work. locationjoystick held 21 unmerged `radin/*` branches and two stale worktrees after their tasks left the backlog, because `reconcile` merged only `done` branches. A follow-up entry keeps the unfinished part on the backlog, at the cost of incomplete work on the base. The tip commit holds the real message, and a bisect should not land on half-built states. A clean merge is a fixed git sequence, and AGENTS.md puts deterministic work in the CLI. A leaf cannot ask, so a product choice in a conflict returns to the router, which asks.
- **`state reconcile`, the session-end report and `prepare` commit a dirty tree instead of skipping or stashing it.** The commit is `wip: update <file names>`, excludes `.radin`, and the output names its hash. **Why:** a skipped reconcile left a finished task blocked and a stash hid the user's own edits, where a dropped or forgotten stash loses them; a commit blocks nothing and loses nothing, and `git reset --soft HEAD~` undoes it.
- **`state leftovers` scans git and the journal repo-wide and only reports.** It prints each `radin/*` branch with a commit the base lacks (worktree, clean, dirty or prunable, journal status, duplicate branches), each `radin-batch:` stash with its task id, and each worktree radin did not create as `foreign`. It reads neither `state/prepared/` nor `completed.json`, and exits 1 when nothing is left. **Why:** a session-scoped list never saw a branch from a crashed or skipped session. Stash triage and `prompt merge` build on this verb.
- **A task whose dependency is done but unmerged stacks on the dependency's `radin/<id>` branch.** `deps_check` counts that dependency as resolved when one unmerged dependency's branch holds every other's tip, and `prepare` cuts the new branch from it and writes `state/stacked/<id>` (parent and parent tip). `reconcile` lands branches by stack depth. For a child whose parent landed it runs `git rebase --onto <base> <recorded parent tip>`, then squashes, so each task lands as its own commit. A child whose parent branch still exists, or conflicted, prints `skipped` and waits. Two unmerged dependencies with no containing tip still block. **Why:** blocking on a merge only the Phase 4.7 landing could grant stalled every dependent in a worktree run. A plain squash of the child would re-apply its parent's changes and conflict.
- **`state wave` prints the ready set from `deps_check` and writes nothing.** It prints `id<TAB>order` per pending task whose dependencies resolve, and claims and blocks nothing. **Why:** the router builds no dependency list by hand, and a read must not change `attempts` or status.
- **`state reconcile` first settles each recorded branch that is gone.** It reads `state/unmerged/<id>` (finished), `state/landing/<id>` (unfinished, written before the squash) and `state/conflict/<id>`. A conflict mark, or work already in the base (`git merge-tree`), records the task. Work outside the base gets its `radin/<id>` branch back from the recorded hash, and the loop lands it. **Why:** the merge leaf deletes a branch after its squash commit, and a task landed by hand under another hash stayed `merge pending` forever. `git cherry` misses both, because a squash of several commits matches no single patch-id. A resolved conflict never merges as a no-op, so its mark is the proof.
- **`preflight` derives its `leftovers` line from `git for-each-ref` and those mark files, with no pipe.** **Why:** `leftovers | grep -q` under `pipefail` failed whenever `grep` exited before the writer finished, so 25 unmerged branches printed no line and the router never ran `reconcile`.
- **A `radin-batch:` stash is compared with every open task and applied, never popped, into the task's tree at `prepare`.** Phase 0 runs `state stash-triage`, which lists each untriaged stash whose changed paths appear in a task file or its plan's `## Changes`. A fact-finder judges each pair, and `state stash-claim` records the verdict. `prepare` runs `git stash apply` after the tree exists. A stash judged irrelevant, or one whose apply fails, stays in `git stash list`. **Why:** the stash message names the task that was about to start, not the owner of the work, and `pop` loses the only copy on a conflict.
- **A sub-agent never spawns a sub-agent.** `lib/radin-leaf-contract.md` states that one flat rule. Prompts carry no concurrency rule.

## The human TUI

- **It draws and dispatches keys, nothing else.** Every mutation shells out to `radin-backlog.sh`. A key that needs a missing operation means a new CLI subcommand, never a write to `index.jsonl`.
- **Raw ANSI only.** No ncurses, `tput`, `dialog`, `gum` or `fzf`. Zero dependencies matches the rest of radin.
- **It is written in C.** **Why:** a bash frame cost a fork per row and about 150 ms per keypress, and the 43 pty tests were a third of the suite's runtime. The build is advisory, so a box with no compiler keeps every other subcommand.
- **A frame is diffed by row and sent in one `write()`** inside DEC mode 2026. Full repaints happen only on the first frame, after a resize, and after a prompt, help or `$EDITOR`/`$PAGER` drew outside the buffer.
- **The first CLI run in a repo migrates `.claude/.radin` and `.agents/.radin` into `.radin`.** `lib/radin-migrate.sh` copies into `.radin.migrating`, renames it to `.radin`, then deletes each source (`git rm` first for a tracked source, so git shows the removal). A second source merges by id: a colliding incoming task takes the suffix `-agents`, with its files and `depends_on` references. Absolute `.claude/.radin` and `.agents/.radin` paths in the index become `.radin`. **Why:** `install.sh` cannot see consumer repos, and a copy first leaves both sources whole after a crash, so the next run redoes the move. The delete runs only after the rename to `.radin`, and a backup copy would sit untracked in the user's repo for good. `completed.json` and `journal.jsonl` keep their old absolute paths, since nothing follows them.
- **The run that creates or migrates `.radin` appends `.radin/` to the repo's `.gitignore`, once.** It skips the append in a non-git directory, when `.radin` is already ignored, and when git tracks `.radin` or a legacy directory. A later run never adds the line back. **Why:** the default is an untracked backlog, and a user who deletes the line keeps it tracked without a marker file.
- **The tree is in creation order.** Only `Shift-A`, `Shift-P`, `Shift-C` and `Shift-T` reorder it, for one session, and the header shows which. **Why:** `c`, `p`, `r` and `D` reload, and nothing may move a row under the cursor. k9s is the reference for any later keybinding question.
- **`o` pages `backlog order --report` verbatim.** **Why:** `Shift-P` sorts by priority, which is not the order `radin-batch` runs, and a human can create that conflict with nothing on screen to show it. The other `order`, `field` and `duplicates` outputs stay LLM-facing and unbound.
- **The detail pane shows facts that are not a sort key.** The list row carries only priority and category, because those two order it. The pane switches between the body and the plan with `l` and `h`. There is no focus concept and no `Tab`. `ctrl-d` and `ctrl-u` scroll the pane and never move the selection.
- **Markdown in the pane is a deliberate subset.** There is no fenced-code state. Lines wrap at build time by display column, not byte, so one buffer entry is one screen line and the scroll offset needs no map.
- **Under 100 columns the pane is not drawn and `enter` opens the renderer full-screen.** **Why:** people read this on a phone.
- **An idle TUI polls `index.jsonl`'s `st_mtime` and `st_size` every 5 seconds.** **Why:** an agent in another terminal writes the same index. It uses seconds and a size because the nanosecond `stat` field needs a platform branch. `RADIN_TUI_POLL_MS` shortens the interval for tests.
- **`w` and `b` write the worktree and branch answers through `radin state session-set`.** **Why:** `state/session.json` stays the one owner of the answers, and `radin-batch` reads it once at its start, so a toggle never splits a run. An unanswered side counts as `no`.
- **`NO_COLOR` keeps attributes and drops colors.** Priority colors use an absolute value map, so no other task's number moves a row's color. Every other color is structural, so nothing reads as a priority.
- **It is not a skill, and no agent invokes it.** Bare `radin` on a terminal runs it. Off a terminal it prints usage and exits non-zero. **Why:** a skill or pipe trapped in a full-screen app would hang the loop until a timeout.
